# Backend contract и перенос на другие MCU

Приложение задаёт **транзакцию на проводах**, backend выбирает механизм исполнения.
Блок DMA, сообщение API и адресная фаза I²C — разные сущности. Их нельзя считать
одним универсальным «transfer step».

## Исследованные платформы

Следующая таблица — требования к будущим портам, не список реализованной поддержки.

| MCU | Особенности, влияющие на backend | Решение для ui2c |
| --- | --- | --- |
| STM32F051 | NBYTES/RELOAD/TC/TCR/AUTOEND, IRQ и DMA; ограничения ES0202 | Реализован собственный регистровый автомат; RX RELOAD побайтно, остальные подходящие блоки DMA |
| MK64 | I²C DMAEN перенаправляет transfer-complete запросы к DMA; прочие события остаются CPU IRQ. Перед последним RX-байтом DMA нужно отключить для TXAK/NACK | IRQ управляет протоколом, eDMA — средней частью буфера. Последний байт/RESTART/ARLO остаются задачей backend |
| ATSAME70Q | TWIHS, XDMAC, internal address и Alternative Command Mode. Обычная host DMA-последовательность оставляет последний TX и два последних RX-байта CPU. High-speed режим TWIHS доступен client, не host | Гибрид IRQ/DMA; аппаратное ускорение распознаваемых транзакций, проверка допустимых RESTART-комбинаций до START; отдельная cache/DMA политика |
| К1921ВГ015 | ST.MODE отражает стадии START, RESTART, ACK/NACK и ARLO; IRQ через RISC-V PLIC. В таблице аппаратных DMA-запросов изученной ревизии I²C отсутствует | Базовый порт — IRQ state machine, без DMA. Критические секции и PLIC completion реализуются платформой |

Источники первичные, изучены 2026-10-11:

- [ST ES0202](https://www.st.com/resource/en/errata_sheet/es0202-stm32f051x4x6x8-device-errata-stmicroelectronics.pdf), разделы I²C и DMA.
- [NXP K64 Reference Manual, rev. 2](https://community.nxp.com/pwmxy87654/attachments/pwmxy87654/kinetis/25442/2/K64P144M120SF5RM.pdf), глава 51, особенно §51.4.9.
- [Microchip DS60001527](https://ww1.microchip.com/downloads/aemDocuments/documents/MCU32/ProductDocuments/DataSheets/SAM-E70-S70-V70-V71-Family-Data-Sheet-DS60001527.pdf), изучена rev. J: главы 35 и 42, особенно §42.7.3.8, Alternative Command Mode и multi-host.
- [НИИЭТ, РП К1921ВГ015, v3 от 24.04.2024](https://niiet.ru/wp-content/uploads/2024/10/%D0%A0%D0%9F-%D0%9A1921%D0%92%D0%93015-v3.pdf), главы 9, 10 (таблица 10.1), 27. Перед реализацией порта нужно сверить актуальную ревизию руководства и конкретный кристалл.

Архитектурный вывод: IRQ является полноценным механизмом асинхронного исполнения.
DMA — локальная оптимизация backend, а не обязательное свойство переносимого API.
Наличие DMA у MCU само по себе не доказывает возможность DMA для его I²C.

## Как написать backend

1. Включить `ui2c_port.h`; вложить `ui2c_t` в статический контекст с собственными
   регистрами/handles, курсорами, DMA descriptors и состоянием протокола.
2. Реализовать четыре обязательные операции `lock`, `unlock`, `start`, `abort`;
   при необходимости добавить `validate` адреса/сообщений и `process` для polling.
3. Board init настраивает clocks, pins, timing, DMA routing и статические параметры
   каналов. В текущем проекте эту роль выполняет CubeMX. Backend init вызывает
   `ui2c_port_init()` для нулевого контекста, сохраняет неизменяемую конфигурацию и
   подготавливает локальную периферию. Внешний BUSY не является ошибкой init;
   init не ждёт освобождения шины и не выполняет GPIO recovery. NVIC/PLIC может быть включён заранее,
   если источники peripheral IRQ/DMA неактивны до завершения backend init.
4. `start()` вызывается под lock, возвращает немедленно. Ошибка означает отсутствие
   активных IRQ/DMA и удерживаемых буферов; успешный возврат принимает запрос.
   Не ждать свободную шину в цикле. При необходимости вернуть BUS_BUSY.
5. IRQ и/или backend `process()` продвигают автомат. Доступны все `bus->msgs` и направление
   следующей границы через `ui2c_port_boundary()`: CONTINUE, RESTART или STOP.
   Разбиение длинных сообщений не должно добавлять START/STOP.
6. После полного завершения I²C **и** всех DMA/RX/cache операций выключить источники
   дальнейшего доступа к буферам и вызвать `ui2c_port_complete()` под той же
   синхронизацией. Приложение из IRQ не вызывается.
7. `abort()` вызывается под lock и синхронно прекращает доступ к request memory.
   Нельзя объявлять DONE, пока DMA ещё пишет RX. Abort не вызывает callback и
   не меняет lifecycle core. Core устанавливает результат CANCELLED/TIMEOUT.

`ops` и контекст backend должны существовать всё время жизни шины; конфигурация
core копируется. `validate(bus, addr, msgs, count)` получает новый адрес явно:
поля запроса в `bus` ещё не обновлены, предыдущая транзакция может быть активна.
Validator вызывается без lock и не должен читать изменяемое IRQ-состояние без
собственной синхронизации.

`start()` может завершить запрос через `ui2c_port_complete()` до возврата,
но тогда обязан вернуть OK. Callback всё равно доставляется только из process.
Нельзя одновременно сообщить completion и вернуть отказ.

## Polling и гибридные backend

Необязательный `ops->process(bus)` вызывается каждым `ui2c_process()` вне lock core,
до чтения clock и проверки timeout. Он выполняет ограниченную неблокирующую работу:
ожидать готовность в цикле нельзя. Backend самостоятельно защищает общие с IRQ поля.
Вызов возможен в IDLE, ACTIVE и DONE; доступ к памяти запроса разрешён только в
ACTIVE. Callback приложения и рекурсивный public API запрещены. Polling backend
без конкурентных обработчиков может использовать пустые lock/unlock.

Наблюдённое completion имеет приоритет над timeout. Это программный таймаут
обслуживания, не гарантия аппаратного дедлайна. После cancel/timeout последующие
вызовы process не должны обращаться к памяти отменённого запроса. Для vendor API
с исключительно блокирующим transfer одного process hook недостаточно.

Приложение всегда вызывает один `ui2c_process()` независимо от IRQ/DMA/polling.
Capabilities описывают только протокол (RESTART, CONTINUE, PROBE). Ошибки DMA
отображаются в IO_ERROR; DMA-каналы, пороги и подробная диагностика принадлежат порту.

`validate()` полезен, если периферия не умеет часть комбинаций сообщений:
проверить всё до первой адресной фазы и вернуть UNSUPPORTED. Capability flags
RESTART/CONTINUE означают доступность операции; не заменяют проверку специфичных
ограничений сочетаний. Нельзя молча подменять RESTART парой STOP+START.

В core нет API смены частоты: TIMINGR, clock tree, фильтры, slew rate и timing
расчёты — ответственность backend/BSP. Разные шины могут иметь разные конфигурации.
Смена timing при работе потребует отдельного, явного idle-only контракта.

## IRQ, память, отмена

`lock/unlock` сериализуют foreground со **всеми** IRQ backend, включая DMA и
вложенные IRQ. Они сохраняют прежнее состояние прерываний и обеспечивают compiler
и memory ordering. `volatile` полей core не заменяет этот контракт. Это не mutex:
под lock нельзя ждать IRQ, SysTick или внешнее устройство.

Для Cortex-M7 нельзя просто направить DMA в произвольный пользовательский RX
buffer и затем invalidate округлённый диапазон cache lines: соседние dirty bytes
могут принадлежать другим объектам. Backend должен выбрать безопасный вариант:
DMA-safe/noncacheable memory, собственный выровненный bounce buffer, либо IRQ
fallback. TX требует корректного clean и проверки доступности памяти для DMA.
Эти правила и cache maintenance принадлежат порту; core ничего не знает о размере
cache line, TCM, XDMAC или архитектуре CPU.

Старое completion-событие не должно завершать новый запрос. Для регистрового порта
нужно отключить источники/каналы и очистить флаги до повторного использования.
Для vendor async API, которое не умеет синхронный abort, потребуется собственная
изоляция/generation и гарантированный quiescence: поздний callback с одним лишь
`bus*` небезопасен. Простого игнорирования второго DONE недостаточно после resubmit.

После потери арбитража не отправлять STOP и не делать GPIO recovery. Повтор записи
может повторить уже выполненное действие устройства; core не решает, безопасно ли это.

## Приёмка нового backend

Использовать тот же набор протокольных сценариев, что в `tests/test_ui2c.c`, с новым
MMIO/vendor adapter. Дополнительно проверить на железе порядок NACK/STOP/IRQ/DMA,
отмену каждой стадии, timing и конкуренцию за память. Для MK64 отдельно проверить
короткие RX и TXAK; для SAME70 — хвосты DMA, ограничения команд и cache canaries;
для К1921ВГ015 — ST.MODE, очистку peripheral IRQ и PLIC claim/complete.

Аппаратные capabilities объявляются только после реализации и проверки. Будущие
порты могут иметь разные оптимизации и ограничения при неизменном `ui2c.h`.
