# Портирование ui2c на новую платформу

[English version](PORTING.md) | [README](README_RU.md)

## Общие принципы

`ui2c` разделяет переносимый контракт I²C-транзакций и аппаратно-зависимую реализацию контроллера.

Приложение описывает транзакцию на шине, а платформенный backend определяет способ её исполнения: через регистры периферии, прерывания, DMA или периодический опрос.

Транзакция, сообщение API, адресная фаза I²C и передача DMA — разные сущности. Backend должен сохранять требуемую последовательность операций на шине независимо от внутреннего разбиения передачи.

Переносимый компонент состоит из:

- `include/ui2c.h` — публичный API приложения.
- `include/ui2c_port.h` — интерфейс backend и общий контекст контроллера.
- `src/ui2c.c` — валидация, жизненный цикл транзакций, тайм-ауты и callbacks.

Аппаратные реализации могут находиться в firmware-проектах либо в самостоятельных репозиториях. Их необязательно размещать внутри `ui2c`.

## Разделение ответственности

| Уровень | Ответственность |
|---|---|
| Приложение / драйвер устройства | Транзакции, протокол устройства, retry, backoff, расписание обменов |
| ui2c core | Валидация, состояние запроса, обнаружение тайм-аутов, доставка callback |
| MCU backend | START/RESTART/STOP, регистры, IRQ, DMA, арбитраж, аппаратные ошибки |
| BSP | Тактирование, pinmux, timing, распределение ресурсов, IRQ routing, экземпляры контроллеров |

Backend не должен содержать логику конкретных I²C-устройств и прикладные алгоритмы повторных передач.

Core не должен зависеть от CMSIS, HAL, RTOS, регистров конкретного микроконтроллера или конфигурации платы.

## Интерфейс backend

Реализация подключает `ui2c_port.h` и предоставляет постоянный контекст, содержащий `ui2c_t` и собственное аппаратное состояние.

Четыре обязательные операции:

| Операция | Назначение |
|---|---|
| `lock()` | Синхронизация foreground с прерываниями backend |
| `unlock()` | Восстановление предыдущего состояния синхронизации |
| `start()` | Неблокирующий запуск транзакции |
| `abort()` | Синхронное прекращение локального доступа к памяти транзакции |

Две необязательные операции:

| Операция | Назначение |
|---|---|
| `validate()` | Проверка аппаратных ограничений без побочных эффектов |
| `process()` | Неблокирующий polling или отложенная аппаратная обработка |

Регистрация выполняется через `ui2c_port_init()`.

Контекст backend, таблица операций и аппаратные ресурсы должны существовать всё время работы экземпляра шины.

Контекст должен быть обнулён перед первой инициализацией.

Инициализация не должна требовать освобождения внешней I²C-шины.

### Синхронизация

`lock()` и `unlock()` защищают общее состояние от конкурентного доступа прерываний.

Они должны:

- Синхронизировать все IRQ backend, включая DMA.
- Сохранять и восстанавливать предыдущее состояние прерываний.
- Обеспечивать корректный порядок операций компилятора и памяти.
- Не ожидать mutex, прерывания или внешнего события.

Для полностью polling-реализации без конкурентных IRQ допускаются пустые функции синхронизации.

Публичный API `ui2c` вызывается только из одного сериализованного foreground-контекста. Конкурентные обращения и вызовы из ISR не поддерживаются.

## Семантика транзакций

Backend получает полное описание транзакции: адрес устройства и массив сообщений.

Адрес передаётся без сдвига. Core использует единое представление 7-битных адресов и предусматривает опциональную 10-битную адресацию.

Первый START и последний STOP формируются неявно.

Для последовательных сообщений:

- `UI2C_MSG_RESTART` требует повторного START перед следующим сообщением.
- Без RESTART передача продолжается без нового START и адресной фазы.
- Смена направления требует RESTART.
- Неподдерживаемые сочетания сообщений отклоняются до начала обмена.

Одиночное сообщение записи с нулевой длиной является address-only probe, если backend поддерживает `UI2C_CAP_PROBE`.

Для определения границы сообщений применяется `ui2c_port_boundary()`, возвращающая CONTINUE, RESTART или STOP.

Внутреннее разбиение сообщений на аппаратные блоки либо DMA-передачи не должно добавлять лишние START и STOP.

## Возможности контроллера

Backend объявляет только фактически реализованные возможности.

| Capability | Значение |
|---|---|
| `UI2C_CAP_RESTART` | Повторный START между сообщениями |
| `UI2C_CAP_CONTINUE` | Продолжение без повторной адресной фазы |
| `UI2C_CAP_PROBE` | Проверка адреса нулевой записью |
| `UI2C_CAP_ADDR_10BIT` | 10-битная адресация |

Capabilities описывают возможности протокола, а не наличие IRQ или DMA.

Если периферия поддерживает возможность только для определённых сочетаний сообщений, backend должен использовать `validate()` для предварительной проверки всей транзакции.

Запрещено незаметно заменять RESTART последовательностью STOP + START.

## Инициализация и жизненный цикл

Типовая последовательность:

1. BSP конфигурирует clock, pins, timing, DMA routing и ресурсы прерываний.
2. Backend проверяет корректность аппаратной конфигурации.
3. Backend вызывает `ui2c_port_init()` с таблицей операций и capabilities.
4. Backend подготавливает локальное аппаратное состояние к выполнению транзакций.

Во время передачи backend обладает исключительным правом управления соответствующей I²C-периферией и выделенными DMA-каналами.

Сторонние драйверы не должны одновременно выполнять операции с тем же контроллером.

Core использует состояния:

`IDLE → ACTIVE → DONE → IDLE`

Успешный результат `ui2c_xfer()` означает принятие запроса, а не физическое завершение передачи.

Каждый принятый запрос завершается ровно одним callback, который доставляется через `ui2c_process()`.

Отклонённый запрос не удерживает буферы и не формирует callback.

### start()

`start()` вызывается под блокировкой backend и должен немедленно возвращать управление.

Ожидать освобождения внешней шины в цикле запрещено.

Если шиной владеет другой контроллер, допустимо вернуть `UI2C_STATUS_BUS_BUSY`.

При ошибке запуска backend обязан оставить локальную периферию в безопасном неактивном состоянии без продолжающегося доступа к буферам.

Разрешено завершить транзакцию непосредственно внутри `start()`, но тогда функция должна вернуть `UI2C_STATUS_OK`. Callback приложения всё равно вызывается позднее через `ui2c_process()`.

### Завершение транзакции

`ui2c_port_complete()` вызывается только после окончательного определения результата, когда аппаратная часть больше не обращается к памяти запроса.

Завершение DMA не обязательно означает завершение I²C-транзакции. Необходимо дождаться соответствующих аппаратных событий, окончания записей DMA и операций с cache.

Backend обязан исключить ситуацию, когда запоздавший IRQ или DMA completion от старого запроса завершает новый запрос.

Callback приложения вызывается вне IRQ и вне critical section.

На момент вызова callback контроллер уже находится в IDLE, поэтому приложение может сразу отправить следующую транзакцию.

### Отмена и тайм-ауты

`abort()` вызывается под блокировкой backend и обязан синхронно остановить все локальные IRQ/DMA обращения к памяти транзакции.

`abort()` не вызывает callback приложения и не изменяет состояние core самостоятельно.

Core завершает отменённый активный запрос с результатом `UI2C_STATUS_CANCELLED` или `UI2C_STATUS_TIMEOUT`.

Если результат транзакции уже зафиксирован, он имеет приоритет перед отменой и тайм-аутом.

Тайм-аут определяется программно при вызове `ui2c_process()`, поэтому приложение должно регулярно обслуживать шину.

Источник времени должен быть монотонным миллисекундным счётчиком `uint32_t`. Допустимый тайм-аут — `1..INT32_MAX` мс. Переполнение счётчика поддерживается, но активный запрос нельзя оставлять без `process()` на полный оборот счётчика.

Это не аппаратная гарантия завершения строго к заданному моменту времени.

Отмена останавливает локальный контроллер, но не гарантирует освобождения SCL/SDA внешним устройством.

## IRQ, DMA и polling

Backend может реализовывать обмен через:

- Прерывания.
- DMA.
- Периодический polling.
- Комбинацию перечисленных механизмов.

Способ исполнения не должен менять публичный API.

Необязательная операция `process()` вызывается из foreground перед проверкой тайм-аута в core. Она должна выполнять ограниченную неблокирующую работу.

Вызов допускается в состояниях IDLE, ACTIVE и DONE. Доступ к памяти текущего запроса разрешён только в ACTIVE.

Backend не должен рекурсивно вызывать публичный API или callbacks приложения.

### DMA и кеш-память

Управление DMA и синхронизация памяти полностью относятся к backend.

На микроконтроллерах с cache необходимо учитывать выравнивание cache lines, операции TX clean и RX invalidate, а также области памяти, недоступные DMA-контроллеру.

Invalidate неполной cache line способен уничтожить соседние изменённые данные. В зависимости от платформы нужно использовать DMA-safe memory, выровненный промежуточный буфер или IRQ fallback.

При отмене backend обязан гарантировать, что отложенная DMA-операция не продолжит доступ к пользовательскому буферу.

## Мультимастерный режим

Backend должен корректно обрабатывать потерю арбитража, занятость внешней шины и особенности аппаратного состояния контроллера.

При потере арбитража необходимо:

- Прекратить локальную обработку передачи.
- Освободить локальные ресурсы, не нарушая обмен выигравшего контроллера.
- Вернуть `UI2C_STATUS_ARBITRATION_LOST`.
- Не генерировать принудительный STOP и не выполнять GPIO bus recovery.

Автоматический retry намеренно отсутствует в контракте core и backend.

Решение о повторе принимает приложение с учётом того, могла ли уже выполниться часть записи во внешнее устройство.

`UI2C_STATUS_BUSY` означает занятость локального программного контекста или ресурса.

`UI2C_STATUS_BUS_BUSY` означает занятость физической I²C-шины.

## Исследованные платформы

Следующие сведения являются результатами предварительного исследования аппаратуры, а не перечнем официально поддерживаемых портов.

| MCU | Аппаратные особенности | Предлагаемая реализация |
|---|---|---|
| STM32F051 | NBYTES, RELOAD, TC/TCR, AUTOEND; errata ES0202 | Регистровый автомат, IRQ/DMA, обход ограничений RX RELOAD |
| NXP MK64 | Взаимодействие DMA-запросов и IRQ-протокола, особая обработка последних RX-байтов | IRQ state machine и опциональный eDMA для средней части передачи |
| ATSAME70Q | TWIHS, XDMAC, internal address, alternative commands; Cortex-M7 cache | Гибридный IRQ/DMA backend с проверкой комбинаций сообщений |
| К1921ВГ015 | События I²C state machine, обработка IRQ через RISC-V PLIC | IRQ state machine; DMA только после подтверждения поддержки конкретной ревизией |

Существующий STM32F051 backend размещён в `ports/ui2c/stm32f0/` firmware-проекта отдельно от переносимого ядра. Его полная аппаратная валидация ещё не завершена.

## Приёмка нового backend

Перед объявлением поддержки новой платформы необходимо проверить:

1. ACK/NACK адреса, address-only probe, обычные чтение и запись.
2. RESTART и CONTINUE без непредусмотренных START/STOP.
3. Длины сообщений на границах возможностей периферии и DMA.
4. NACK, потерю арбитража, BUS_BUSY, timeout и cancel.
5. Отсутствие запоздалых IRQ/DMA обращений после отмены или завершения.
6. Возможность повторного обмена после ошибок.
7. Работу при конкуренции нескольких контроллеров, если она требуется.
8. Errata конкретного MCU, timing, cache, DMA и взаимодействие прерываний.

Аппаратные проверки желательно выполнять с логическим анализатором.

Успешная компиляция не подтверждает сама по себе корректность I²C-протокола или устойчивость мультимастерного режима.
